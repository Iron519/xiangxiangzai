产品定位：服务小微客户的智能客服产品，但并非直接用户触点，而是管理端。所以其各项功能是支持解耦的，包括用户触点（chat API）和管理功能。
产品受众：需要7*24的智能客服，并且回答内容基于内部知识的小微商家。
使用成本：大模型Token成本
接下来将以用户使用流程为顺序，逐节点解读其功能和设计理念。
一、登陆
现阶段仅支持账号密码登录，原因有二：一是免费；二是即便现在做了复杂的登陆功能，未必就合乎客户的意愿，到时候再加也来得及。
但毕竟产品消耗的是我自己的千问大模型额度，为避免恶意注册和滥用，设计两层防御：
1. 用户注册+批准制，用户首次注册不能直接成功，而是会提交一个申请（需备注理由），我通过数据库软删功能控制；
2. 在使用过程中，首先用户只能使用特定范围内的知识，并且我会监测用户用量，后台控制额度上限。
二、鉴权
权限分为横向和纵向——
横向来讲：一个平台支持多位客户上传知识，定制特色流程，所以用户一定要与业务绑定，但是好就好在，不存在单一用户具有横跨多业务的情形（1:1），所以用户本身就能代表业务，无需维护映射关系；
纵向来讲：一个业务下面，所有用户是否有权限看到所有模块（对话、报表、洞察、用户管理...），我们先明确这款产品的用户，是业务管理者而非使用者，所以他应能看到所有自身相关的内容，至于终端用户（chat user），只要使用chat的API即可
所以鉴权表只需要一张，维护全部内容，包括：用户uid、用户名、密码、申请理由、是否批准（软删）、备注。而客户的终端用户与客户共用一个账号密码，相当于产品的access key
由于一个access key只对应一个用户，至于被多少人使用无法区分，也就无法给客户做用户管理。目前该问题无需解决，等有客户接入后，根据它自身的用户登录鉴权机制，再重建一份数据库，uid换成客户的终端用户，加以统计。
三、知识管理
首先是支持所有文件的上传和解析，这个过程是异步并发的，准备一个容量为3的连接池，第4个请求需排队，但不会阻塞进程，前面的文件上传完毕自动处理排队文件。
上传文件后，系统会将文件存储到upload_kb目录下，上传者uid对应的文件夹，并以文件上传名称作为文件名，如果有重名的，则会覆盖旧文件，在用户上传时，一旦重名，系统会加以提示。对于文件名，系统本身没有限制（空格、波浪线都行）
解析的中间结果会存储在fetch_knowledge/parse_result目录下，上传者uid对应的文件夹中，有两个文件是必然生成的，一是merged.md，这是最后的解析结果markdwon；二是anchors.json，这是建立图片与内容文字映射关系（即便没有图片也会生成），其余文件则是当上传内容非纯文本时进行渲染和minerU识别的中间结果。
用户可以在前端页面实时查看文件解析进度，进度分为两个环节，一是”解析完成“，此时文件落到知识列表中，并可以查看全文解析结果，二是”注入完成“，此时可以查看全文切片结果。
当文件在解析时，用户可以点击按钮停止进程，后台的文件解析立即停止，并且过程性文件全部删除；当文件解析完毕，已经进入切片+嵌入的注入阶段，前台没有停止按钮，但用户可以编辑全文/切片，后台将对编辑后结果重新嵌入。
对于已完成入库的文件，用户仍可在前台删除，删除后，parse_result目录下同步删除，但是upload_kb中加以保留（以备追查），kb_chunks的PG表中同步删除
